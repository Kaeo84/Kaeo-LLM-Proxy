Request-log coverage

        

          Every request reaching the proxy's port is logged with the status the client was actually given, and is
          routed to the log that matches how it was answered — Proxy when a model was called,
          Non-proxied when it was answered without one. Previously the rows were written but
          mislabelled — RequestLog defaulted to Success / code 0
          and no error path overrode it, so a 404 was indistinguishable from a 200. Two paths produced no row at all,
          and the automated probes buried real traffic. All four gaps are closed.

Root cause

          
RequestLog defaults made an error indistinguishable from a success:


public RequestStatus Status { get; set; } = RequestStatus.Success;   // enum member 0
public int StatusCode { get; set; }                                 // 0

          

            Nothing in the error paths overrode them. log.StatusCode was assigned in sixteen places,
            every one a success path, an upstream-status copy, or a gated-noise stub.
            No proxy-originated error path ever set it. The 404 branch set neither field, so an
            unrecognised caller could not be found by any filter.

The two paths that produced no row

            
Both are now logged:

            
    
              
  1. 
                503 overload rejection — RejectOverloadedAsync runs in
                ProxyServer before HandleAsync, so no RequestLog existed and no
                logging finally could run. It now calls
                OllamaProxyHandler.RecordRejectedRequest before attempting the response write,
                since the client may already be gone but the request was still answered on the proxy's port.
              
    2. 
              
  2. 
                GET / and HEAD / health probes — these returned before the
                try owning the logging finally. HandleCoreAsync now wraps its
                entire body in one try/finally, so no branch can escape logging. They are
                classified into the HealthProbes capture category.

Splitting non-proxied traffic

            

              Logging every request exposed a second problem: the frequent probes and static endpoints drowned the
              requests that actually reached a model. Non-proxied traffic now has its own store, its own SQLite table
              (non_proxied_requests), and its own Logs → Non-proxied tab.
            

            

              A request is non-proxied when the proxy answered it without calling a model.
              Classification is by method + path (IsModelRoute), never by status code:
              UpstreamPath is assigned optimistically before the body is parsed, and a 400 the proxy
              produced is indistinguishable from a 400 relayed from upstream.

              Each category is an independent toggle on the Settings tab, replacing the single
              collect_all_traffic switch (kept in the schema only for ordinal stability). The defaults
              capture real client API calls and every rejection while leaving the multi-second pollers off.
              LocalStubs is on deliberately: GitHub Copilot polls /v1/models, so treating
              stubs as noise would make real client traffic vanish silently.
            

          

        


        

          
Caller attribution

          

            Logging every request made the noise problem obvious: a HEAD / probe produces a
            row with no model, no upstream, and no body — nothing to tell you who sent it. Every
            request now captures the caller's identity so any row is traceable:
          

          

            

              
FieldSourceWhy it helps

              
                

                  ClientAddress
                  req.RemoteEndPoint (IPv4-mapped IPv6 normalised)
                  Identifies the socket the request came from
                

                

                  UserAgent
                  req.UserAgent
                  Names the calling tool — a VS probe vs a browser vs a script — in one glance
                

              
            

          

          

            Both are set once in HandleAsync and RecordRejectedRequest, so every path that
            produces a row is attributed, including the pre-routing 503. They persist as nullable columns on
            requests, mcp_requests, and non_proxied_requests (baseline DDL
            and an AddColumnIfMissing migration, so an existing database gains them), and
            the detail pane shows a Client / Agent line after Path — only when
            present, so older rows simply omit it.
          

          

            This does not change what is logged
            

              Probes are still gated by their capture category. Attribution only makes those rows
              actionable when you turn that category's capture on to see who is probing.
            

          

        


        

          
Header capture

          

            Attribution names who called; headers say what they sent. Every request now captures its
            full header block, and every response captures its own, persisted as request_headers and
            response_headers on all three tables. This is what makes a body-less request — a probe, an
            unknown endpoint — diagnosable, since the headers name the client library, content type, and any
            tracing/correlation headers.
          

          

            Credential values are always masked
            

              Authorization, Proxy-Authorization, Cookie, Set-Cookie,
              Api-Key, and any *-token / *-secret / *-password /
              *-auth / *-key name is replaced with [REDACTED]
              independently of the redaction settings — a log that stores a bearer token is a
              credential leak, and the value has no diagnostic worth the risk. The header name is kept so the
              request stays traceable. The block is truncated at 32 KB so a pathological header set cannot bloat
              every row.
            

          

        


        

          
Non-proxied bodies

          

            Non-proxied rows previously carried no payload, so an unknown app hitting the proxy gave nothing to look
            at. The branches that answer without a model — the health probe, /api/version, the 501
            unsupported-call path, and the 404 unknown-endpoint path — now capture both the caller's payload and the
            proxy's error body.
          

          

            Unmapped payloads stay readable
            

              A mapped request's body is prompt content, so whole-body redaction is the default there. A request with
              no mapping (an unknown endpoint by definition) is not carrying a prompt, and its payload is the main
              reason to capture it, so it gets field-level redaction instead: credentials and known sensitive
              fields are still masked, but the payload structure stays readable.
            

          

        


        

          Out of scope
          

            Truly malformed HTTP — bad request line, invalid headers, garbage bytes — is rejected by Windows
            http.sys with a 400 before any managed code runs. HttpListener exposes no
            callback for it. Capturing that layer would require replacing HttpListener with a raw
            TcpListener plus hand-rolled HTTP parsing. Per your decision, this implementation covers
            everything the proxy process actually receives.

Fix design

        

          The gap was that status metadata got set at each individual resp.StatusCode = N assignment, so any
          path that forgot it silently logged a success. The fix centralises the rule into one derivation helper, routes
          every error branch through a single recorder, backfills defensively in one finally, and closes the
          two paths that produced no row at all. All steps are implemented and tested.
        


        

          
One rule, one place

          
RequestLog.DeriveStatus — added to Kaeo LLM Proxy Core/Models/RequestLog.cs:


internal static RequestStatus DeriveStatus(int statusCode) => statusCode switch
{
    499 => RequestStatus.Cancelled,
    >= 400 => RequestStatus.Error,
    0 => RequestStatus.Error,   // no response recorded
    _ => RequestStatus.Success,
};

          

            0 → Error matters because RequestStatus defaults to Success. An
            unanswered request silently appearing successful is what made undeliverable errors invisible.
            499 → Cancelled keeps a user abandoning a request out of the error count, so it is not
            charged against upstream reliability.
          

        


        

          
Log before the response

          
RecordResponseStatus — every proxy-originated error now goes through here:


private static void RecordResponseStatus(HttpListenerResponse resp, RequestLog log, int statusCode)
{
    log.StatusCode = statusCode;              // ← written first
    log.Status = RequestLog.DeriveStatus(statusCode);
    resp.StatusCode = statusCode;             // can throw once headers committed
}

          

            Why the order matters
            

              HttpListenerResponse.StatusCode throws once the response has committed its headers —
              which a streaming request does early for SSE. Recording first means the entry still carries the code
              the proxy intended to send when that happens.
            

          

        


        

          
Precedent already in the codebase

          

            McpServerHost.HandleRequestSafeAsync (lines 253–254) already derives both fields from the
            response in one place:
          


log.StatusCode = context.Response.StatusCode;
log.Status = log.StatusCode >= 400 ? RequestStatus.Error : RequestStatus.Success;

          

            The proxy never got the equivalent backfill. The same pattern applies, with two caveats the MCP host does
            not have to handle:
          

          
    
            
  • 
              A streaming request pre-commits SSE headers, so resp.StatusCode may not reflect what the
              client actually received. Prefer the code passed to TryWriteErrorResponseAsync, and only fall
              back to resp.StatusCode.
            
    • 
            
  • 
              PassthroughCoreAsync sets log.StatusCode from the upstream response. A
              backfill must only fill a zero, never overwrite that.
            
    • 
            
  • 
              The backfill must only escalate, never downgrade. The passthrough failure at
              "headers already committed" sets Status = Error while leaving StatusCode at the
              upstream's 200, because that status line is already on the wire. Deriving unconditionally
              would flip a genuine failure back to Success — reintroducing the very bug class this fix
              exists to remove. So the derived status is applied only while the entry is still at its
              Success default.
            
    • 
          

          

            Why the finally skips the exception path
            

              The unhandled-exception handler logs the entry itself so it can attach the exception detail, so the
              finally skips both the backfill and a second AddLog. That avoids a duplicate row,
              but the stronger reason is a race: AddLog hands the same RequestLog
              instance to the background persistence channel, so mutating it afterwards would race that write.

A race worth knowing about

          

            A handler writes and closes the response before HandleCoreAsync's logging
            finally runs. So a client can observe the status code while the log entry does not exist yet.
            This is inherent to the design, not a defect — but it means a test that asserts immediately after receiving
            a response will fail intermittently, passing or failing on scheduling alone.
          

          

            RequestLoggingCoverageTests therefore polls TotalRequests — which
            AddLog increments after enqueueing — instead of asserting straight away. Verified deterministic
            across four consecutive full-class runs. Anything asserting on log contents after a live request needs the
            same wait.
