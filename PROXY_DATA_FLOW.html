Why invalid calls look unlogged

        

          They are being logged — they are mislabelled. The finally block in
          HandleCoreAsync calls _stats.AddLog(log) unconditionally, so every request that reaches the
          routing table produces a row. What is missing is the status metadata, which makes those rows invisible to any error filter.

Root cause

          
RequestLog defaults are the reason an error is recorded as a success:


public RequestStatus Status { get; set; } = RequestStatus.Success;   // enum member 0
public int StatusCode { get; set; }                                 // 0

          

            Nothing in the error paths overrode them. log.StatusCode was assigned in sixteen places in
            OllamaProxyHandler — every one a success path, an upstream-status copy, or a
            CollectAllTraffic stub. No proxy-originated error path ever set it.

            Worst case
            

              The 404 branch set neither field, so an unknown-endpoint call was indistinguishable from a
              successful one. That is exactly the "unknown app call" you wanted to surface — and it was the
              one response that could not be found by any filter.

          Out of scope
          

            Truly malformed HTTP — bad request line, invalid headers, garbage bytes — is rejected by Windows
            http.sys with a 400 before any managed code runs. HttpListener exposes no
            callback for it. Capturing that layer would require replacing HttpListener with a raw
            TcpListener plus hand-rolled HTTP parsing. Per your decision, this implementation covers
            everything the proxy process actually receives.

Fix design

        

          The gap is that status metadata was set at each individual resp.StatusCode = N assignment, so any
          path that forgot it silently logged a success. The fix centralises the rule and closes the two unlogged paths.
        


        

          
One rule, one place

          
RequestLog.DeriveStatus — added to Kaeo LLM Proxy Core/Models/RequestLog.cs:


internal static RequestStatus DeriveStatus(int statusCode) => statusCode switch
{
    499 => RequestStatus.Cancelled,
    >= 400 => RequestStatus.Error,
    0 => RequestStatus.Error,   // no response recorded
    _ => RequestStatus.Success,
};

          

            0 → Error matters because RequestStatus defaults to Success. An
            unanswered request silently appearing successful is what made undeliverable errors invisible.
            499 → Cancelled keeps a user abandoning a request out of the error count, so it is not
            charged against upstream reliability.
          

        


        

          
Log before the response

          
RecordResponseStatus — every proxy-originated error now goes through here:


private static void RecordResponseStatus(HttpListenerResponse resp, RequestLog log, int statusCode)
{
    log.StatusCode = statusCode;              // ← written first
    log.Status = RequestLog.DeriveStatus(statusCode);
    resp.StatusCode = statusCode;             // can throw once headers committed
}

          

            Why the order matters
            

              HttpListenerResponse.StatusCode throws once the response has committed its headers —
              which a streaming request does early for SSE. Recording first means the entry still carries the code
              the proxy intended to send when that happens.
            

          

        


        

          
Precedent already in the codebase

          

            McpServerHost.HandleRequestSafeAsync (lines 253–254) already derives both fields from the
            response in one place:
          


log.StatusCode = context.Response.StatusCode;
log.Status = log.StatusCode >= 400 ? RequestStatus.Error : RequestStatus.Success;

          

            The proxy never got the equivalent backfill. The same pattern applies, with two caveats the MCP host does
            not have to handle:
          

          
    
            
  • 
              A streaming request pre-commits SSE headers, so resp.StatusCode may not reflect what the
              client actually received. Prefer the code passed to TryWriteErrorResponseAsync, and only fall
              back to resp.StatusCode.
            
    • 
            
  • 
              PassthroughCoreAsync sets log.StatusCode from the upstream response. A
              backfill must only fill a zero, never overwrite that.
