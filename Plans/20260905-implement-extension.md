# Plan: Kaeo VS 2026 Extension (Copilot-style) — implementation status

## Architecture (final)
- **No Copilot SDK runtime dependency.** The Copilot SDK is used only as a design reference
  (for agent/mode/tool interaction patterns and VS pairing), not as a runtime library.
- **Model calls** → the proxy's Ollama-compatible API (`/api/chat` NDJSON streaming, `/api/tags`).
  OLLAMA standards only; OpenAI is intentionally NOT used yet.
- **Tool execution** → MCP clients (`McpServerManager`: HTTP Streamable JSON-RPC real, stdio stubbed).
- **VS interaction** → standard VSSDK (tool window, command bar).
- **Custom `AgentRuntime`** follows the SDK's patterns: sessions, `AgentMode`
  (Interactive/Bypass/AutoPilot), permission handlers, streaming events, tool loop
  (max 10 iterations), AutoPilot continuation budget (default 5).

## Multi-connection / model flow (per user correction)
- **No hardcoded proxy URL.** Connections live in `settings.jsonc` (name, baseUrl, apiKey, enabled).
- **Settings → Models tab**: add a connection (name + URL + optional key); a **Refresh models**
  button re-pulls `/api/tags` per connection and updates the tree in place.
- **Ollama `/api/tags` parsed per standard**: `models[].name`, `details.context_length`,
  `capabilities[]`. Tool-calling is detected via the Ollama-native `"tools"` capability token
  (the proxy's `BuildOllamaCapabilities` maps the operator's `function_calling` → `"tools"`).
- Tool-capable models are **auto-enabled** for tool use; the model pill shows `connection / model`
  and routes requests to the owning connection's `OllamaApiClient`.
- Default model = first tool-capable model, else the first model.

## Projects
- `Kaeo LLM Proxy VS Extension.Core` (net10.0 class library, no VS SDK deps):
  - `OllamaApiClient` — `/health`, `/api/tags`, `/api/chat` NDJSON streaming, optional bearer key
  - `AgentRuntime` — agent loop, modes, tool execution, AutoPilot
  - `McpServerManager` — HTTP Streamable JSON-RPC (`tools/list` + `tools/call`), stdio stub, tool schema build
  - `ExtensionSettingsStore` — JSONC at `%APPDATA%\KaeoVsExtension\settings.jsonc`
	(connections+models, agents, mcpServers, defaults, logging)
  - `ExtensionLogger` — Serilog file sink, level-driven
  - `ChatEngine` — UI facade (routes a turn to a per-connection client)
- `Kaeo LLM Proxy VS Extension` (VSIX, net10.0-windows, VS 18.0 targets):
  - WPF tool window (transcript, Agent/Mode/Model pills, prompt box, gear → settings)
  - `ToolWindowViewModel` — binds UI to `ChatEngine`, streaming, live model pull, permission routing
  - 4-tab settings modal (General/Models/Agents/MCP); Models tab adds connections + refresh
  - `source.extension.vsixmanifest` (schema-valid, VS 18.0, amd64), `Commands.vsct`, `VsPackage.cs`
  - csproj: `Microsoft.VSSDK.BuildTools` 18.5.40034, `VSSDKBuildToolsAutoSetup`, `GeneratePkgDefFile=false`

## Build / packaging status
- **Full solution builds: 0 errors.**
- `GeneratePkgDefFile` is set to `false` in the VSIX csproj because the CLI `CreatePkgDef` tool is
  a .NET Framework executable that cannot load net10.0-windows type references
  ("Unable to load type from reference"). The `.pkgdef` (package registration file) is generated by
  the **Visual Studio IDE** VSIX build instead.
- The `.vsix` container itself builds via CLI.

## How to test
1. **Run (fastest):** set the startup project to `Kaeo LLM Proxy VS Extension`, press F5. VS opens an
   experimental instance. View → Tool Windows → Kaeo Assistant.
2. **Install:** build the VSIX project in **Release** (IDE, so the `.pkgdef` is generated), then
   Extensions → Manage Extensions → Install from File → the `.vsix` at
   `Kaeo LLM Proxy VS Extension\bin\Release\net10.0-windows10.0.22000.0\win-x64\*.vsix`.
- Prereqs: the Kaeo LLM Proxy running with at least one enabled model mapping.
- Add a connection (⚙ → Models) with the proxy's base URL; models pull live from `/api/tags`.
