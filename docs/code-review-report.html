#1 — async void on non-event-handler method can crash the processMainForm.cs:289

ApplyMcpServerSettingsAsync is declared async void but is called from OnMcpSettingChanged — it is not a WinForms event handler. If an unhandled exception propagates out of this method, it will crash the entire process with no opportunity for recovery.

// MainForm.cs line 289
private async void ApplyMcpServerSettingsAsync()
{
    // ...
    try { await _mcpServer.ApplySettingsAsync(); }
    catch (Exception ex) { Log.Error(ex, "Failed to apply MCP server settings"); }
    // ...
}

Recommendation: Change the signature to private async Task ApplyMcpServerSettingsAsync() and have the caller use _ = ApplyMcpServerSettingsAsync(); or await it. The log-on-error pattern is correct, so the only risk is an exception thrown outside the try/catch (e.g. before the try block).

#2 — Task.Wait() in Dispose blocks thread for up to 5 secondsStatisticsService.cs:464

_persistTask?.Wait(TimeSpan.FromSeconds(5)) synchronously blocks the calling thread during shutdown. If Dispose is called from the UI thread, this freezes the dashboard for up to 5 seconds. If multiple services dispose on the same thread, the time accumulates.

// StatisticsService.cs line ~464
public void Dispose()
{
    _cleanupTimer?.Dispose();
    if (_persistChannel is not null)
    {
        _persistChannel.Writer.TryComplete();
        try { _persistTask?.Wait(TimeSpan.FromSeconds(5)); }  // <-- BLOCKING
        catch (Exception ex) { Log.Warning(ex, "..."); }
    }
}

Recommendation: Replace with await _persistTask by making Dispose async, or use a fire-and-forget continuation with a timeout via Task.WhenAny / CancellationTokenSource.CancelAfter. If the Dispose pattern cannot change to async, at least push the wait onto Task.Run so the caller is not blocked.

#5 — Thread.Sleep in retry loop blocks thread-pool threadExtensionSettingsStore.cs:135

A synchronous file write with a retry loop using Thread.Sleep(50 * attempt) blocks the calling thread for up to 1.2 seconds (sum of sleeps for 8 attempts). This method is in the VS Extension project targeting .NET Framework 4.8.

// ExtensionSettingsStore.cs ~line 135
for (var attempt = 1; ; attempt++)
{
    try
    {
        using (var stream = new FileStream(path, FileMode.Create, ...))
        using (var writer = new StreamWriter(stream, Encoding.UTF8))
        { writer.Write(text); }
        return;
    }
    catch (IOException) when (attempt < maxAttempts)
    {
        Thread.Sleep(50 * attempt); // 50, 100, 150 ... ms — BLOCKING
    }
}

Recommendation: Use await Task.Delay(50 * attempt, cancellationToken) with an async retry helper. If the method cannot become async due to its caller, push the whole retry to Task.Run and await the result, or use a SpinWait for very short waits.

#6 — ConnectionHealthStat uses public mutable fields accessed from multiple threadsStatisticsService.cs:490

The ConnectionHealthStat class exposes all its state as public fields (Attempts, Failures, Count, LastError, etc.) and is stored in a ConcurrentDictionary. Updates happen via Interlocked.Increment on some fields but not on others. Reads happen from the UI thread without any synchronization, so a read can observe a partially updated state.

// StatisticsService.cs ~line 490
internal sealed class ConnectionHealthStat  // <-- public fields!
{
    public long Attempts;
    public long Count;
    public long Failures;
    public long LastAttemptUtcTicks;
    public long LastSentUtcTicks;
    public string LastStatus = "Not checked";
    public string LastError = string.Empty;
}

Recommendation: Replace public fields with properties backed by Interlocked.Read/Interlocked.Exchange or use a snapshot pattern (copy under a lock before exposing). ConnectionHealthSnapshot (the record) already exists for this purpose; ensure all reads go through Snap().

#7 — Broad catch (Exception) with log-only recovery obscures root causesMultiple files

At least 25 sites catch Exception generically and only log a message, effectively swallowing errors that might indicate corruption, threading violations, or resource exhaustion. Notable examples:

  • TrayApplicationContext.cs:107,135,162 — Start/stop/restart proxy failures
  • MainForm.cs:1405,1726,2807,2934,3047,3130,3240 — Various UI refresh paths
  • StatisticsService.cs — persistence drain timeout

Recommendation: Catch and log specific exception types where the failure mode is understood. Reserve generic Exception catches only for top-level boundary handlers where the process must not crash, and always include the full exception (not just ex.Message) in the log context.

#9 — Static HttpClient _explorerSpecClient without lifecycle managementOllamaProxyHandler.cs:7490

A static HttpClient is created inline for fetching API explorer specs. Static HttpClient instances are well-known to cause DNS change issues in long-running processes (they cache DNS indefinitely on .NET Core when no handler is configured). While this client has a 5-second timeout, it lacks PooledConnectionLifetime and will retain stale DNS entries forever.

// OllamaProxyHandler.cs ~line 7490
private static readonly HttpClient _explorerSpecClient = new() { Timeout = TimeSpan.FromSeconds(5) };

Recommendation: Use SocketsHttpHandler with PooledConnectionLifetime like the main BuildHttpClient() does, or use IHttpClientFactory.

// MeaiAdapter.cs line 93
json["content"] = result.Result?.ToString() ?? content;

Here result is a FunctionResultContent instance and Result is a property of type object?, but the syntax is identical to blocking on a Task<object>.Result. A reader (or Copilot) scanning this line will flag it as a potential deadlock.

#11 — HttpClient disposal races against in-flight requests via pollingOllamaProxyHandler.cs:120

When settings change, a new HttpClient is created and the old one is disposed via a fire-and-forget Task.Run that polls an _inFlightRequests counter with a 250ms interval for up to 5 minutes. This is a fragile timing contract: if a request thread increments the counter between the poll and the dispose, the old client gets disposed while still in use.

_ = Task.Run(async () =>
{
    DateTime deadline = DateTime.UtcNow.AddMinutes(5);
    while (Volatile.Read(ref _inFlightRequests) > 0 && DateTime.UtcNow < deadline)
        await Task.Delay(TimeSpan.FromMilliseconds(250));
    // ... 
    old.Dispose();  // <-- possible race
});

Recommendation: Use a reference-counted handle (e.g. a wrapper that increments on checkout and decrements on return) rather than checking a flat counter. Or accept that disposing a pooled HttpClient while connections are open may throw ObjectDisposedException and catch that.

#13 — AddIfMissing uses O(n) linear scan on List<string>CapabilityDetector.cs:179
private static void AddIfMissing(List<string> list, string token)
{
    if (!list.Any(t => string.Equals(t, token, StringComparison.OrdinalIgnoreCase)))

Linear scan on a small list (at most ~6 capability tokens) so the performance impact is negligible. A HashSet<string> with an ordinal-ignore-case comparer would be more idiomatic.

The clone itself is fine (it's done before the volatile write), but any code that reads _settings.SomeProperty multiple times in a single method may see values from two different snapshots if the field is replaced between reads.
