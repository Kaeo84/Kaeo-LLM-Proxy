Kaeo LLM Proxy

View on GitHub Releases Documentation

Kaeo LLM Proxy is a cross-platform, Ollama API-compatible proxy in front of one or more llama.cpp servers and other OpenAI-compatible upstreams. It lets Ollama clients and OpenAI-style SDKs talk to backends that only expose a /v1/ API — and wraps that in a built-in web dashboard with users, roles, API keys, per-user model and tool access, usage analytics, and a full request / stream / sys-log viewer.

It ships as a Windows system-tray application and as a headless host for Linux and macOS, both running the same engine and the same dashboard.

Why this exists

Many local AI tools expect the Ollama REST API, while llama.cpp and similar servers expose an OpenAI-compatible API. This proxy sits in between, listening on localhost:11434 by default, rewriting requests and responses as needed, and routing each request to the correct upstream model. The dashboard, the access control, and the logging exist because a local proxy quickly becomes a shared proxy: several people, several clients, several keys, one backend.

Highlights

Protocol translation

  • Ollama ↔ OpenAI/llama.cpp request and response translation
  • Transparent /v1/* passthrough for OpenAI-compatible clients and SDKs
  • Streaming (NDJSON) and non-streaming completions
  • Copilot-compatible SSE framing — well-formed data: [DONE], synthesized usage chunk, in-band errors
  • Streaming tool-call rewriting, including inline XML tool-call conversion
  • Vision (base64 image) passthrough for multimodal models
  • Model name mapping with per-model upstream URL, timeout, credential, sampling, and behavior settings

Reasoning and thinking

  • Ollama think input, message.thinking output, and reasoning_content compatibility
  • Per-model reasoning effort: value list, selection, Client App / Proxy / Provider priority
  • Multiple upstream wire formats — top-level reasoning_effort, nested reasoning, Qwen Cloud extra_body, chat_template_kwargs
  • Per-model Thinking Handling: leave inline <think> blocks, move them into reasoning fields, strip them, or handle Qwen [Thinking]/[Answer] markers
  • Per-model context-window reporting so clients such as GitHub Copilot meter context accurately

Long conversations

  • Automatic context compaction per model mapping, with a chosen summarization target
  • Manual compaction routing — /v1/chat/completions/compact and /v1/responses/compact
  • Global Copilot compaction target, because Copilot will not honor a per-model choice
  • Configurable summary ceiling, fallback context window, and compaction concurrency
  • Streaming heartbeats plus upstream heartbeat monitoring with a live per-model view

Web dashboard

  • Served by the engine itself on ListenPort + 1 — no IIS, no Node, no second process
  • Login-only by default, with first-run administrator setup from the local machine
  • Eleven tabs, filtered by the roles the signed-in account holds
  • Light, dark, and follow-system themes
  • Optional HTTPS from a certificate held in the credential store

Access security

  • Users with name, email, dashboard login, and any combination of seven roles
  • API keys per user, hashed for authentication and encrypted so an Admin can reveal or regenerate them
  • Model and MCP grants on the user, inherited by every key that user holds
  • Admin always reaches every model, every tool, and every tab
  • Rate-limited sign-in, protected session cookies, and immediate session revocation

MCP server and modules

  • Built-in Model Context Protocol server over Streamable HTTP at /mcp
  • Optional Scalar API explorer and OpenAPI document
  • Importable .kaeomod modules contributing tools in isolation (Web Search, SSH, Code Vector Store)
  • Package signing, per-module configuration, and per-user MCP access
  • Optional capture of MCP request/response details with field-level redaction

Observability

  • Request log in SQLite, auto-archived by size and auto-expired by age
  • Requestor column attributed by API key, plus method, path, model, status, duration, and token counts
  • Live SSE stream panel with upstream and client byte counts
  • Application log viewer with level filters, search, and heartbeat hiding
  • Token usage analytics by period, model, and user, with per-day drill-down
  • Manual refresh, or automatic at 5, 10, 30, or 60 seconds

Operations

  • Start, stop, and restart the proxy, the MCP server, and the web server — from the dashboard and the tray app
  • CPU, working set, GC, and per-source traffic counters on the dashboard
  • Centralized encrypted credential store referenced by name from mappings, modules, and HTTPS
  • Request/response redaction, including field-level redaction of sensitive JSON keys
  • Portable: everything lives in a Data/ folder beside the executable

Web dashboard

The dashboard is the same UI on every platform and covers everything the tray app does. It is served by the engine itself — no separate process, no IIS, no Node.

  • Address: http://localhost:11435 by default (ListenPort + 1). Set WebDashboard.Port to override, or WebDashboard.ListenAddress to bind wider than loopback.
  • TLS: set WebDashboard.Scheme to Https and point WebDashboard.CertificateCredentialName at a certificate credential created on the Credentials tab. The dashboard, the proxy, and the MCP endpoint all serve that certificate.
  • Access: WebDashboard.RequireLogin is on by default. Turning it off gives everyone who can reach the port full Admin access — only appropriate on an isolated network.

Roles

Roles combine — the permissions are the union — so a user can be, say, User Admin plus Dashboard Read Only. A user with no valid role has no dashboard access at all rather than falling back to Read Only.

RoleWhat it adds
AdminEverything: every model, every MCP tool, every tab, and every action
Read OnlyThe Requests log and Usage, limited to that user's own traffic
Dashboard Read OnlyThe Dashboard tab — state, performance, and traffic totals, without the control buttons
Dashboard Read-WriteDashboard Read Only plus start, stop, and restart for the proxy, the MCP server, and the web server
User AdminRead Only plus adding, updating, and removing users, roles, API keys, and grants
Model AdminRead Only plus adding, updating, and removing model mappings
Test ConsoleThe Test Console tab, limited to the models that user can access

Sys Log, the live stream panes, and the Settings, Credentials, and Modules surfaces stay Admin-only whatever else is granted, because they expose payload text and stored secrets.

Users, API keys, and grants

  • Users carry a name, an email address, an optional dashboard login, one or more roles, and the grants that decide what their API keys can reach.
  • Model and MCP access belong to the user, not to an individual key, so every key that user holds has the same reach. An empty allowed-model list means no models, not all models.
  • API keys are hashed for authentication and also kept under reversible encryption, so an Admin can reveal or regenerate one. Regenerating keeps the label and the grants and invalidates the old secret immediately.
  • Card actions live behind a 3-dot overflow menu, so a card stays readable however many keys it holds.
  • Proxy API keys never grant dashboard access — they authenticate model and MCP requests only.

Model discovery, /api/show, chat, and passthrough all honour the caller's grants: a model that is disabled or hidden disappears from /api/tags and /v1/models, and a model the caller cannot reach is refused.

MCP server and modules

The proxy embeds an MCP server (default http://localhost:8388/mcp) that exposes the tools contributed by the loaded modules over the Streamable HTTP transport. Clients speak JSON-RPC 2.0: post an initialize request to open a session (the response carries an Mcp-Session-Id header), then send tools/list and tools/call on the same session.

Modules are importable .kaeomod packages built against the module contracts. The host loads each in an isolated context and contributes its tools, configuration, and help content. Ships with:

  • Web Search — web_search / web_fetch tools
  • SSH — remote shell execution tools
  • Code Vector Store — semantic code indexing and search (code_index, code_search, code_status, and more)

MCP clients authenticate with a proxy API key or the configured shared bearer credential. A known key whose user lacks the MCP grant gets 403; an unknown key gets 401. Only the /health probe stays open. Module packages are per-platform, so a Windows package will not load on macOS or Linux.

Configuration highlights

  • ListenPort and ListenAddress configure where the proxy listens; a separate MCP section (port, address, auth, API explorer) controls the /mcp endpoint, and a web dashboard section controls the UI listener.
  • The Logging section controls app logs, retention, and the SQLite database location.
  • Model mappings define the proxy-facing name, upstream model, upstream URL, timeout, credential, and feature toggles.
  • Per-model settings cover thinking compatibility, streaming heartbeats, summarization, instruction sets, response redaction, context-window override, reasoning effort, and compaction.
  • Credentials store named secrets and certificates encrypted at rest, referenced by name from model mappings, module providers, and the HTTPS listener.
  • Users, roles, API keys, and grants live in the same database and are edited from the Users tab in either GUI.

Quick start (Windows)

  1. Install the .NET 10 Desktop Runtime if needed.
  2. Run Kaeo LLM Proxy.exe; it starts minimised to the system tray.
  3. Open the dashboard from the tray icon, or browse to http://localhost:11435.
  4. Create the first administrator account when the dashboard offers first-run setup.
  5. Add one or more model mappings that point at your llama.cpp or compatible upstream servers.
  6. Add a user and an API key, then grant that user the models and MCP access it should have.
  7. Point your Ollama-compatible client at http://localhost:11434 with that key.

Linux and macOS

The headless host runs the same engine without the tray icon, as a single self-contained executable so no .NET SDK is needed on the target machine: 

# Apple Silicon
dotnet publish "src/Kaeo LLM Proxy Headless/Kaeo LLM Proxy Headless.csproj" \
  -c Release -r osx-arm64 --self-contained true -o artifacts/osx-arm64

# Linux x64
dotnet publish "src/Kaeo LLM Proxy Headless/Kaeo LLM Proxy Headless.csproj" \
  -c Release -r linux-x64 --self-contained true -o artifacts/linux-x64

Copy the output folder to the target machine and run ./Kaeo LLM Proxy Headless. The same Data/ layout is created beside the executable, so the folder stays portable. On first launch no dashboard account exists yet, so browse to the dashboard port and the login page offers first-run setup. SIGINT/SIGTERM drains in-flight requests and shuts down cleanly.

The Windows-only pieces (the tray app and the Visual Studio extension) are not part of the headless host. Build module packages on the target platform with ./Kaeo LLM Proxy Headless --module-pack <module-dir>, adding --module-sign --key <private-key.pem> to sign them.

Networking and security

  • Default binding is localhost for the proxy, the MCP server, and the dashboard.
  • Binding to 0.0.0.0 or a specific external IP may require administrator rights or a URL ACL reservation, for both the proxy listener and the MCP server on its own port.
  • Keep WebDashboard.RequireLogin on whenever the dashboard is reachable beyond loopback.
  • Prefer request/response redaction when prompts or outputs may contain sensitive information.
  • Use HTTPS upstream endpoints, and an HTTPS dashboard certificate, when traffic crosses a network you do not control.
  • The MCP server supports a bearer credential and field-level redaction of sensitive JSON keys when capturing request/response details.
