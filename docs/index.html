Kaeo LLM Proxy

View on GitHub Releases Documentation

Kaeo LLM Proxy is a cross-platform LLM proxy with a built-in web dashboard. It speaks the Anthropic, OpenAI/ChatGPT, and Ollama APIs on the front door and forwards each request to whatever your backends actually speak — llama.cpp or any other OpenAI-compatible server, a real Ollama server, or the Anthropic Messages API — translating requests, responses, and streams in both directions. Around that engine it adds user administration, API keys, a credential store for central model management, custom prompt injection, and comprehensive logging, reporting, and statistics.

Runs on Windows, macOS, and Linux. The engine — proxy, MCP server, dashboard, users, keys, logging, statistics — is identical on all three, and so is the dashboard served from it. The web GUI is the cross-platform GUI: only the system-tray app and the Visual Studio extension are Windows-only. On macOS and Linux the headless host runs the same engine and serves the same dashboard, so nothing is lost but the tray icon.

Why this exists

It started as a bridge: many local AI tools expect the Ollama REST API while llama.cpp and similar servers expose an OpenAI-compatible one, so the proxy sat in between and translated. The same idea turned out to be useful for everything else — ChatGPT-style clients, Anthropic clients, several backends at once, per-user access control, and one place to see what every client is actually doing. Clients still point at localhost:11434; what sits behind that port is now configurable, multi-protocol, and auditable.

API translation — Anthropic, OpenAI, Ollama

The proxy is not tied to one protocol on either side. Clients may speak any of the three supported protocols, and each model mapping may point at any of the three, so one listener can serve an Ollama client, a ChatGPT-style client, and an Anthropic client at the same time while fronting a mixed fleet of backends.

Ollama GET /api/tags, GET /api/ps, GET /api/version, POST /api/show, POST /api/chat, POST /api/generate, POST /api/embeddings, POST /api/embed

Upstream — what a mapping points at

UpstreamTypeUpstream APITypical target
OpenAI/v1/chat/completions, /v1/completions, /v1/embeddings, /v1/modelsllama.cpp, vLLM, LM Studio, OpenRouter, OpenAI
Ollama/api/chat, /api/generate, /api/embeddings, /api/tagsa real Ollama server
AnthropicPOST /v1/messagesapi.anthropic.com, or a gateway in front of it

EnableApiTranslation (default on) is per mapping: with it on, an Ollama or Anthropic request is rewritten into the upstream's native shape and the answer — streaming or not — is rewritten back into the shape the client asked for. That covers tool/function calls (tool_calls ↔ tool_use/tool_result), base64 images, system prompts, stop sequences, sampling parameters, finish reasons, and token usage. With it off the request is forwarded verbatim, for when client and upstream already speak the same protocol and you only need routing. Anything the target protocol cannot express is dropped rather than sent as an invalid field. Anthropic requires max_tokens, so a mapping to an Anthropic upstream supplies it (default 4096) and sends anthropic-version (default 2023-06-01) on every call.

Highlights

Protocol translation

  • Anthropic, OpenAI/ChatGPT, and Ollama on the front door — any client protocol, any mapping protocol
  • Bidirectional translation of requests, responses, and streams, including tool calls, images, system prompts, and token usage
  • Transparent /v1/* passthrough for OpenAI-compatible clients and SDKs
  • Streaming (NDJSON for Ollama, SSE for OpenAI and Anthropic) and non-streaming
  • Copilot-compatible SSE framing — well-formed data: [DONE], synthesized usage chunk, in-band errors
  • Streaming tool-call rewriting, including inline XML tool-call conversion
  • Vision (base64 image) passthrough for multimodal models
  • Model name mapping with per-model upstream URL, timeout, credential, sampling, and behavior settings

Reasoning and thinking

  • Ollama think input, message.thinking output, and reasoning_content compatibility
  • Per-model reasoning effort: value list, selection, Client App / Proxy / Provider priority
  • Multiple upstream wire formats — top-level reasoning_effort, nested reasoning, Qwen Cloud extra_body, chat_template_kwargs
  • Per-model Thinking Handling: leave inline <think> blocks, move them into reasoning fields, strip them, or handle Qwen [Thinking]/[Answer] markers
  • Per-model context-window reporting so clients such as GitHub Copilot meter context accurately

Long conversations

  • Automatic context compaction per model mapping, with a chosen summarization target
  • Manual compaction routing — /v1/chat/completions/compact and /v1/responses/compact
  • Global Copilot compaction target, because Copilot will not honor a per-model choice
  • Configurable summary ceiling, fallback context window, and compaction concurrency
  • Streaming heartbeats plus upstream heartbeat monitoring with a live per-model view

Web dashboard

  • Served by the engine itself on ListenPort + 1 — no IIS, no Node, no second process
  • Login-only by default, with first-run administrator setup from the local machine
  • Eleven tabs, filtered by the roles the signed-in account holds
  • Light, dark, and follow-system themes
  • Optional HTTPS from a certificate held in the credential store

Access security

  • Users with name, email, dashboard login, and any combination of seven roles
  • API keys per user, hashed for authentication and encrypted so an Admin can reveal or regenerate them
  • Model and MCP grants on the user, inherited by every key that user holds
  • Admin always reaches every model, every tool, and every tab
  • Rate-limited sign-in, protected session cookies, and immediate session revocation

Central model management

  • Named credential store for API keys, bearer tokens, username/password pairs, SSH private keys, and certificates
  • Referenced by name from model mappings, module providers, and the HTTPS listener — rotate once, every consumer follows
  • AES-256-GCM at rest with a PBKDF2-derived key; the passphrase hash is DPAPI-protected on Windows
  • Write-only after saving — the GUI shows only a masked value and whether a secret is set
  • Certificate credentials configure HTTPS for the dashboard, the proxy, and the MCP endpoint

Custom prompt injection

  • Named instruction sets injected into every request a mapping serves — no client edits
  • Attached per model mapping, with a separate set for compaction summaries
  • Merged with the client's own system messages into exactly one system message, so strict templates such as Qwen3 keep working
  • Editable next to the mapping it applies to, in either GUI

MCP server and modules

  • Built-in Model Context Protocol server over Streamable HTTP at /mcp
  • Optional Scalar API explorer and OpenAPI document
  • Importable .kaeomod modules contributing tools in isolation (Web Search, SSH, Code Vector Store)
  • Package signing, per-module configuration, and per-user MCP access
  • Optional capture of MCP request/response details with field-level redaction

Logging, reporting, and statistics

  • Request log in SQLite, auto-expired by age (72 hours by default, configurable or forever)
  • One row per request: date, time, requestor, client label, method, path, model, status, duration, and token counts
  • Source split — Proxy, MCP, Web dashboard traffic, and Non-proxied requests
  • Live SSE stream panel with upstream and client byte counts
  • Application log viewer with level filters, search, and heartbeat hiding
  • Token usage analytics by period, model, and user, with per-day drill-down
  • Counters for requests, errors, prompt/completion tokens, and requests per second, plus per-model heartbeat health
  • Request/response redaction, including field-level redaction of sensitive JSON keys
  • Manual refresh, or automatic at 5, 10, 30, or 60 seconds

Operations

  • Start, stop, and restart the proxy, the MCP server, and the web server — from the dashboard and the tray app
  • CPU, working set, GC, and per-source traffic counters on the dashboard
  • Centralized encrypted credential store referenced by name from mappings, modules, and HTTPS
  • Request/response redaction, including field-level redaction of sensitive JSON keys
  • Portable: everything lives in a Data/ folder beside the executable

Web dashboard

The dashboard is the same UI on every platform and covers everything the tray app does. It is served by the engine itself — no separate process, no IIS, no Node.

  • Address: http://localhost:11435 by default (ListenPort + 1). Set WebDashboard.Port to override, or WebDashboard.ListenAddress to bind wider than loopback.
  • TLS: set WebDashboard.Scheme to Https and point WebDashboard.CertificateCredentialName at a certificate credential created on the Credentials tab. The dashboard, the proxy, and the MCP endpoint all serve that certificate.
  • Access: WebDashboard.RequireLogin is on by default. Turning it off gives everyone who can reach the port full Admin access — only appropriate on an isolated network.

Roles

Roles combine — the permissions are the union — so a user can be, say, User Admin plus Dashboard Read Only. A user with no valid role has no dashboard access at all rather than falling back to Read Only.

RoleWhat it adds
AdminEverything: every model, every MCP tool, every tab, and every action
Read OnlyThe Requests log and Usage, limited to that user's own traffic
Dashboard Read OnlyThe Dashboard tab — state, performance, and traffic totals, without the control buttons
Dashboard Read-WriteDashboard Read Only plus start, stop, and restart for the proxy, the MCP server, and the web server
User AdminRead Only plus adding, updating, and removing users, roles, API keys, and grants
Model AdminRead Only plus adding, updating, and removing model mappings
Test ConsoleThe Test Console tab, limited to the models that user can access

Sys Log, the live stream panes, and the Settings, Credentials, and Modules surfaces stay Admin-only whatever else is granted, because they expose payload text and stored secrets.

Users, API keys, and grants

  • Users carry a name, an email address, an optional dashboard login, one or more roles, and the grants that decide what their API keys can reach.
  • Model and MCP access belong to the user, not to an individual key, so every key that user holds has the same reach. An empty allowed-model list means no models, not all models.
  • API keys are hashed for authentication and also kept under reversible encryption, so an Admin can reveal or regenerate one. Regenerating keeps the label and the grants and invalidates the old secret immediately.
  • Card actions live behind a 3-dot overflow menu, so a card stays readable however many keys it holds.
  • Proxy API keys never grant dashboard access — they authenticate model and MCP requests only.

Logging, reporting, and statistics

Every request is logged — nothing lives only in memory — and four sources share one SQLite database and one set of retention rules, so "who called what, when, from which client, with which key, and what happened" is answerable without correlating files.

ReportWhat it gives you
Requests One row per request with date, time, requestor, client label, method, path, model, status, duration, and token counts. Bodies, headers, and error text are fetched only when a row is opened, so the list stays fast against a large database. Live streams are tailed in the same tab, capped to fifteen rows, and a click opens that stream's captured upstream and forwarded tails in a dialog.
Sources Proxy traffic, MCP tool calls, Web dashboard traffic, and Non-proxied requests that were refused or not handled — so a scanner hitting an unknown path shows up as a row instead of silently vanishing.
Sys Log The application's own Serilog output with level filters, model filter, text search, and heartbeat hiding. Heartbeat ping failures have their own threshold so an upstream that is switched off cannot bury real errors. Admin-only, because it can contain payload fragments.
Usage Token consumption by day, week, or month and by model, scoped to your own traffic or — for Admin — to any user with a per-user share breakdown.
Statistics Total requests, total errors, prompt and completion tokens, requests per second, per-model counts, and a live connection-health snapshot of heartbeat probes and failures per model.
Performance CPU, working set, GC gen2 collections, and LOH size sampled for the Dashboard card.

Retention is by age: LogRetentionHours defaults to 72 hours and 0 keeps rows forever. Only the newest entries retain bodies, which bounds memory without losing metadata. Per mapping, RedactRequestBodies and RedactResponseBodies replace captured bodies with a marker (both on by default), RedactSensitiveJsonFields scrubs keys, tokens, and passwords while leaving prompt text readable, and Authorization headers are always redacted.

Central model management

API keys, bearer tokens, username/password pairs, SSH private keys, and certificates are stored once in a credential store and referenced by name from wherever they are needed — model mappings, module providers, and the HTTPS listener. A fleet of mappings shares one rotating secret instead of holding N copies of it.

  • Encrypted at rest. AES-256-GCM with a key derived from your security passphrase via PBKDF2-SHA256 (600,000 iterations). The passphrase is never stored — only its SHA-256 hash, which is DPAPI-protected on Windows. On macOS and Linux the hash is stored without DPAPI, so protect the Data/ folder with filesystem permissions.
  • Write-only after saving. No GET ever returns secret material: the GUI shows a masked value and whether a secret is set. Leave a field blank while editing to keep the stored secret, or supply a new value to replace it.
  • Certificate credentials carry a certificate and private key, which is how HTTPS for the dashboard, the proxy, and the MCP endpoint is configured.
  • The name is the contract. Renaming a credential breaks every consumer, so the GUI warns before doing it.

Custom prompt injection

Named instruction sets inject your own system prompt into every request that a mapping serves, without editing each client. An instruction set is a name, a description, and the instruction text; a mapping attaches one, and mappings that attach none are untouched.

The text is merged with any leading system messages the client already sent into exactly one system message, separated by blank lines. Strict chat templates — Qwen3, for example — reject a second system message, so folding rather than prepending is what keeps those models working. A separate compaction instruction set tunes the prompt used when the proxy summarises a conversation, independently of the answering prompt.

Model discovery, /api/show, chat, and passthrough all honour the caller's grants: a model that is disabled or hidden disappears from /api/tags and /v1/models, and a model the caller cannot reach is refused.

MCP server and modules

The proxy embeds an MCP server (default http://localhost:8388/mcp) that exposes the tools contributed by the loaded modules over the Streamable HTTP transport. Clients speak JSON-RPC 2.0: post an initialize request to open a session (the response carries an Mcp-Session-Id header), then send tools/list and tools/call on the same session.

Modules are importable .kaeomod packages built against the module contracts. The host loads each in an isolated context and contributes its tools, configuration, and help content. Ships with:

  • Web Search — web_search / web_fetch tools
  • SSH — ssh_connect, ssh_exec, ssh_disconnect, ssh_list
  • Code Vector Store — semantic code indexing and search (code_index, code_search, code_sync_repo, code_list_collections, code_status, code_reindex, code_remove)
  • Chat Interface — chat_send, chat_ask, chat_read, chat_channels for Discord, Microsoft Teams, Slack, Google Chat, and Zoom

MCP clients authenticate with a proxy API key or the configured shared bearer credential. A known key whose user lacks the MCP grant gets 403; an unknown key gets 401. Only the /health probe stays open. Module packages are per-platform, so a Windows package will not load on macOS or Linux.

Configuration highlights

  • ListenPort and ListenAddress configure where the proxy listens; a separate MCP section (port, address, auth, API explorer) controls the /mcp endpoint, and a web dashboard section controls the UI listener.
  • The Logging section controls app logs, retention, and the SQLite database location.
  • Model mappings define the proxy-facing name, upstream model, upstream URL, UpstreamType (OpenAI, Ollama, or Anthropic), EnableApiTranslation, timeout, credential, and feature toggles.
  • Per-model settings cover thinking compatibility, streaming heartbeats, summarization, instruction sets, response redaction, context-window override, reasoning effort, and compaction.
  • Anthropic upstreams take AnthropicMaxTokens and AnthropicApiVersion, applied when the client omits them.
  • Credentials store named secrets and certificates encrypted at rest, referenced by name from model mappings, module providers, and the HTTPS listener.
  • Users, roles, API keys, and grants live in the same database and are edited from the Users tab in either GUI.
  • A wildcard listen address (0.0.0.0, ::) is an instruction to listen everywhere, not a browsable destination — wherever the app hands you a URL it reports http://localhost:<port> instead, so Open Web Dashboard always works.

Quick start

  1. Windows: install the .NET 10 Desktop Runtime if needed and run Kaeo LLM Proxy.exe; it starts minimised to the system tray. macOS/Linux: run the self-contained ./Kaeo LLM Proxy Headless (see below).
  2. Open the dashboard — from the tray icon on Windows, or by browsing to http://localhost:11435 anywhere.
  3. Create the first administrator account when the dashboard offers first-run setup.
  4. Add one or more model mappings: the name clients will use, the upstream URL, and the protocol the backend speaks.
  5. Add a user and an API key, then grant that user the models and MCP access it should have.
  6. Point your client — Ollama, OpenAI/ChatGPT-style, or Anthropic — at http://localhost:11434 with that key.

Linux and macOS

The headless host runs the same engine without the tray icon, as a single self-contained executable so no .NET SDK is needed on the target machine: 

# Apple Silicon
dotnet publish "src/Kaeo LLM Proxy Headless/Kaeo LLM Proxy Headless.csproj" \
  -c Release -r osx-arm64 --self-contained true -o artifacts/osx-arm64

# Linux x64
dotnet publish "src/Kaeo LLM Proxy Headless/Kaeo LLM Proxy Headless.csproj" \
  -c Release -r linux-x64 --self-contained true -o artifacts/linux-x64

Copy the output folder to the target machine and run ./Kaeo LLM Proxy Headless. The same Data/ layout is created beside the executable, so the folder stays portable. On first launch no dashboard account exists yet, so browse to the dashboard port and the login page offers first-run setup. SIGINT/SIGTERM drains in-flight requests and shuts down cleanly.

The Windows-only pieces (the tray app and the Visual Studio extension) are not part of the headless host. Build module packages on the target platform with ./Kaeo LLM Proxy Headless --module-pack <module-dir>, adding --module-sign --key <private-key.pem> to sign them.

Visual Studio extension

A Windows-only companion extension adds a GitHub Copilot-style chat panel that pairs with the proxy: an agent/mode/model pill bar, a streaming chat transcript, a multi-tab settings modal, and MCP tool integration, all routed through the proxy's Ollama-compatible API. It ships with Interactive, Bypass, and AutoPilot agent modes, built-in Agent / Ask / Plan agents plus user-defined ones, and support for any number of proxy connections — models are pulled live from each connection and tool-capable models are auto-enabled.

Networking and security

  • Default binding is localhost for the proxy, the MCP server, and the dashboard.
  • Binding to 0.0.0.0 or a specific external IP may require administrator rights or a URL ACL reservation, for both the proxy listener and the MCP server on its own port.
  • A wildcard bind is a listen instruction, not a destination: every URL the app hands you — the tray menu's Open Web Dashboard, the Dashboard tab, the headless startup line — is normalised to http://localhost:<port>, and IPv6 literals are bracketed so the URL stays valid.
  • Keep WebDashboard.RequireLogin on whenever the dashboard is reachable beyond loopback.
  • Prefer request/response redaction when prompts or outputs may contain sensitive information.
  • Use HTTPS upstream endpoints, and an HTTPS dashboard certificate, when traffic crosses a network you do not control.
  • The MCP server supports a bearer credential and field-level redaction of sensitive JSON keys when capturing request/response details.
